## Model parity notes

All package models match the donor field for field. Deltas found, all acceptable:

- Donor `Project.course` points at its `Cohort` model; the package renames the field to `cohort`.
- Donor `ProjectSubmission.github_link` carries `validate_url_200` in addition to `URLValidator`.
  That donor validator performs live HTTP status checks (transport imported lazily). The package
  keeps only syntax validation; live status checks stay a site concern.
- Donor implicit related name `projectsubmission_set`; the package sets `related_name="submissions"`.
- Donor `faq_contribution_url` is validated by `clean_faq_contribution_url`
  (`courses/validators/url_status_transport.py`) as a GitHub issue or pull request URL. That is a
  product rule and stays site-side; the package service only strips and stores the value
  (equivalence note for D5.x).
- `criteria_for_project` is identical, including the legacy cohort fallback gated on
  `curriculum_format == "legacy"`.
- `CourseLeaderboard`, complaints and enrollment rollups are C5.2d scope; `LeaderboardComplaint`
  already exists in the package models.

The donor splits one scoring pipeline over five modules for readability only; the package keeps
the scoring pipeline in one `review.py` module and the learner-facing submission service in
`projects.py`, matching the C5.2b layout (`scoring.py`, `statistics.py`).

One deliberate assignment-pool change: the package excludes `volunteer_review_only=True`
placeholder submissions from the required-review pool. The donor would include placeholders when
an operator resets a project to `COLLECTING_SUBMISSIONS` after volunteers signed up; reviewing a
placeholder submission is meaningless, so the pool holds real submissions only.

## Peer review assignment behavior

- Preconditions, in order, each returning `(FAIL, message)` without raising:
  state must be `COLLECTING_SUBMISSIONS`; `submission_due_date <= now`;
  `len(submissions) > project.number_of_peers_to_evaluate`.
- The selection algorithm validates the same size condition and raises `ValueError` when
  `num_submissions <= num_reviews_each`; the service pre-check makes that unreachable.
- Seeding: `random.seed(seed)` on the global module. The service calls it with `seed=42`; the
  selection function default is `seed=1`. Keep both constants.
- One reviewer per submission, iterated in submission list order. Each reviewer reviews exactly
  `num_evaluations` distinct submissions and never their own.
- Slot pools: for each of the `num_evaluations` slots a pool starts as all submission indices and
  shrinks globally as reviewers take projects, balancing how often each submission is reviewed.
- Per reviewer, a `selected` set starts with their own index; a slot picks a random slot-pool entry
  not in `selected`; when the slot pool has none, the fallback picks any index not in `selected`.
- Reviews are created with `state=TO_REVIEW`, `optional=False`, via one `bulk_create`.
- Success opens the review window inside the same transaction:
  `peer_review_due_date = ceil_to_next_hour(now + 7 days)` (donor `PEER_REVIEW_WINDOW`), then
  state becomes `PEER_REVIEWING`.
- `ceil_to_next_hour` lives in donor `course_management.deadlines`; the package has no equivalent.
  Add a small helper (next full hour, UTC-aware) in the coursework app.

## Scoring behavior

Grouping (`group_peer_reviews`):

- Loads all `CriteriaResponse` for the review set in one query, grouped by `review_id`.
- Builds `submissions` (by id), `reviews_by_submission`, `reviews_by_reviewer`.
- Only `SUBMITTED` reviews attach to the two review maps; `TO_REVIEW` rows still register their
  submission, so unreviewed submissions get scored too. `review.responses` receives the in-memory
  response list.

Evaluation score (`calculate_project_score`):

- `CriteriaResponse.get_scores`: blank or null answer means `[0]`; otherwise the answer is
  comma-separated one-based indices into `criteria.options`, mapped to their `score` values.
  `get_score` is their sum.
- Zero submitted reviews for a submission: per criterion fallback
  `criteria.median_score()`: `RB` type is `ceil(statistics.median(option scores))`, `CB` type is
  `ceil(sum(option scores) / 2)`. The total sums all criteria.
- With reviews: group responses by criterion across the submission's submitted reviews; per
  criterion, score is `ceil(statistics.median(response.get_score() for responses))`. Criteria with
  no responses are skipped, not scored as zero. Total is the sum of per-criterion values. Each
  criterion value becomes a `ProjectEvaluationScore` row.

Per-submission scoring (`score_submission`):

- `project_score` is the evaluation total above.
- `peer_review_score` is `mandatory_reviews_given * project.points_for_peer_review`, where
  mandatory counts this learner's submitted, non-optional reviews.
- `peer_review_learning_in_public_score` is 0 when `enrollment.disable_learning_in_public`;
  otherwise the sum over submitted reviews of `min(len(review.learning_in_public_links),
  project.learning_in_public_cap_review)`.
- `project_learning_in_public_score` is 0 when disabled or when the submission has no links;
  otherwise `min(len(links), project.learning_in_public_cap_project)`.
- `project_faq_score` is 1 when `faq_contribution_url` is set with length >= 5, else 0.
- `total_score` is the sum of the five components above.
- `reviewed_enough_peers` is mandatory reviews given >= `project.number_of_peers_to_evaluate`.
- `passed` is `project_score >= project.points_to_pass and reviewed_enough_peers`, where
  `points_to_pass` reads `cohort.project_passing_score`.

`score_project` service:

- Preconditions, in order, each returning `(FAIL, message)` without raising:
  `points_to_pass != 0`; state is `PEER_REVIEWING`; `peer_review_due_date <= now`; the project has
  at least one `PeerReview`.
- `bulk_update` on submissions covers exactly: `project_score`, `project_faq_score`,
  `project_learning_in_public_score`, `peer_review_score`,
  `peer_review_learning_in_public_score`, `total_score`, `reviewed_enough_peers`, `passed`.
- Evaluation scores are replaced, not merged: delete all `ProjectEvaluationScore` rows for the
  project's submissions, then `bulk_create` the new set.
- Project state becomes `COMPLETED` and is saved inside the transaction.
- A pass-ratio summary string is returned as the success message.

## Votes behavior

- `PROJECT_VOTES_PER_PROJECT = 3`.
- `update_project_vote(user, submission, action="vote")`: `action="remove"` deletes the voter's
  vote for that submission. Adding is a no-op when the vote exists or when the voter already has
  three votes across submissions of the same project; otherwise `get_or_create`.
- `get_voted_submission_ids(user, course)` returns the set of submission ids the user voted for
  inside the cohort; empty set for anonymous users.
- `get_project_vote_counts(user, course)` returns this user's vote count per project id; empty
  dict for anonymous users.

## Volunteer review behavior

From `courses/views/project_eval_actions.py`, to extract as services:

- Volunteer submission defaults in the donor: `github_link="https://github.com/DataTalksClub/course-management-platform"`,
  `commit_id="volunteer"`. The URL is site-branded; the package service should take the defaults
  as an argument and DTC passes its constant (record the equivalence note for D5.1).
- Reviewer identity is a `ProjectSubmission`, not a user. The service resolves the caller's real
  submission (`volunteer_review_only=False`); when absent it `get_or_create`s the `Enrollment`
  for (user, cohort) and then a volunteer `ProjectSubmission` with
  `volunteer_review_only=True` and the defaults above.
- A volunteer may review only non-volunteer submissions that are not their own; the review is
  `get_or_create`d with `optional=True`.
- Removal deletes only reviews where `optional=True` and the reviewer is the caller's submission.

## AISL mapping (issue step 4, documentation only)

AISL's light project flow lives in `content/models/peer_review.py`:

- AISL `ProjectSubmission` (unique per user and course; `project_url`, `description`, status
  lifecycle `submitted`/`in_review`/`review_complete`/`certified`, nullable `cohort` for
  self-paced, `batch_assigned_at`, `review_deadline`, `certificate_issued_at`) becomes package
  `ProjectSubmission` under one package `Project` per AISL cohort. `project_url` maps to
  `github_link`; `commit_id` has no donor source and stays empty. Status maps to `Project.state`:
  `submitted` to `COLLECTING_SUBMISSIONS`, `in_review` to `PEER_REVIEWING`,
  `review_complete` and `certified` to `COMPLETED`.
- AISL `PeerReview` (`reviewer` is a `User`, single nullable `score` 1..5, `feedback`,
  `is_complete`, unique per submission and reviewer) becomes package `PeerReview` plus a
  `CriteriaResponse`. The package `PeerReview.reviewer` needs a `ProjectSubmission`; the mapping
  creates the user's volunteer submission when no real one exists. Each mapped project gets one
  `ReviewCriteria` whose option scores are 1..5 with the AISL criteria text (A5.1 fixes the text);
  the review's numeric score becomes the response answer.
- AISL self-paced submissions (null cohort) attach to the `self_paced` cohort and its project, per
  A5.1 step 2.
- AISL `CourseCertificate` stays outside this flow; A5.1 maps it with the curriculum surfaces.
- A5.1 applies this mapping; C5.2c only records it.
