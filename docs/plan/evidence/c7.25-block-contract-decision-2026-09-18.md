# C7.25 decision: shrink the block surface, then check the one slot that is left

Date: 2026-09-18. Repository: community-base. Issue: C7.25, `docs/plan/phase-7.md`.

Step 3 of the issue is a decision and it is taken here, before any code, because it determines
what the check in step 2 is even checking.

## The defect, restated in terms of who owes what

Django drops the content of a block the parent template does not define. No exception, no warning,
nothing in the logs. `docs/02-architecture.md` section 5 has asked a consuming site's `base.html`
for five block names since the architecture was written: `title`, `meta_description`,
`page_head_metadata`, `content`, `extra_js`. Nothing has ever verified that a site supplies them,
and neither site supplies all five.

Measured on the package tree at this commit, 41 templates extend `base.html`:

| Block | Templates filling it | AISL base | DTC base |
|---|---|---|---|
| `content` | 41 | absent (it uses `body`) | present |
| `title` | 40 | present | present |
| `meta_description` | 23 | present | absent |
| `page_head_metadata` | 2 | present | absent (it uses `meta_robots`) |
| `extra_js` | 3 | absent (it uses `extra_scripts`) | present |

Neither site is careless. Each has a perfectly coherent naming scheme for its own chrome; the
package asked both of them to adopt a third one and told neither.

## Decision

Two changes, in this order.

1. Package public templates stop extending the site's `base.html` directly. They extend a
   package-owned adapter, `community_base/public/base.html`, shipped by `community_base.kernel`.
   The adapter's entire body is `{% extends "base.html" %}`: on a site whose base already names the
   blocks the way section 5 says, it is a pass-through and changes nothing. A site whose base names
   them differently overrides that one path in its own `templates/` directory and maps its names
   onto the contracted ones, in three or four lines, once, for all 41 pages.

   For AI-Shipping-Labs that file is:

   ```
   {% extends "base.html" %}
   {% block body %}{% block content %}{% endblock %}{% endblock %}
   {% block extra_scripts %}{% block extra_js %}{% endblock %}{% endblock %}
   ```

   Django resolves blocks by name across the whole inheritance chain rather than by lexical
   nesting, so the inner `content` block is reachable by a page template whether the site's base
   renders the outer `body` or names its own slot `content`. This is the same mechanism the Studio
   shell already relies on with `content` wrapping `studio_content`.

2. A Django system check reads the adapter's resolved inheritance chain and reports every
   contracted block that no template in the chain defines, naming the block and an offending
   package template.

## What this changes about the size of the contract

The count of block names does not fall: the package still fills five. What falls is what a site
has to do about them, and where the cost lands.

Before: five names in the site's own top-level `base.html`, a file that every page on the site
inherits from, imposed by the package on the site's own vocabulary. AISL's answer to that demand
was to copy all three package knowledge-base templates into its own `templates/` and rename
`content` to `body` in each — three forked templates, permanently diverging from the package, to
avoid touching its base. That is the real cost of a wide contract stated in the site's own
namespace, and it was already being paid.

After: one small template at a path the package names, in the site's own directory, which the site
writes once and which no package release overwrites. The package stops reaching into the site's
chrome vocabulary at all.

## What was rejected

A check that enforces the current wide contract and nothing else. It would have been correct and
much smaller, and it would have told both sites to go and add package-named blocks to their own
`base.html`. That is the demand the architecture has been making silently for a year, and making
it loudly does not make it a good demand: it asks a site to adopt package vocabulary in the one
file it is least willing to change, and it leaves AISL's three forked knowledge-base templates
looking like the reasonable workaround they currently are.

Shrinking to a single wrapper block, `cb_content`, with the head blocks dropped from the contract.
This was the first thing tried on paper. It fails on `page_head_metadata`: the two mail pages use
it to emit `noindex, nofollow`, and a single body wrapper has nowhere to put head content. Dropping
the head blocks would not shrink the contract, it would move the failure from "the block is
dropped" to "the package can no longer say the thing at all", which is worse for exactly the two
pages the issue names.

Renaming the package's block names to a `cb_`-prefixed set. It buys nothing the adapter does not
already buy, and costs an edit to all 41 templates plus a rename in the two sites that currently
match on some names. The adapter means the package's names stay private to the package side of the
adapter, which is the property that was actually wanted.

Making the package's default adapter guess, by shipping
`{% block body %}{% block content %}{% endblock %}{% endblock %}` as the default so AISL passes
untouched. It works, and it was rejected: `body` is one site's private name, the package has no
business knowing it, and a site whose base happens to define both `body` and `content` would render
the page body twice.

Selecting the adapter from a setting, `{% extends cb_public_base %}` with a context processor. It
makes every package view depend on a context processor being installed, and the failure mode when
it is not is a confusing render-time error rather than a check-time one. Path override is the
mechanism the Studio shell already uses and the one a site already knows.

## Severity: an error for `content`, a warning for the other four

Not one severity for all five, because they do not fail alike.

`content` unreachable means the page has a head, a title, the site's chrome, and no body. There is
no reading under which serving that is acceptable, and 41 of 41 templates fill it. It is an
`Error`, and a site with it cannot start.

`title`, `meta_description`, `page_head_metadata` and `extra_js` unreachable each lose something
real and none of them lose the page. A missing title or description falls back to the site's
default. A missing `page_head_metadata` loses a `noindex` on two public pages, which is a genuine
harm but a slow one, and DTC has a coherent robots story under its own block name that a package
error has no right to call broken. A missing `extra_js` leaves the static page correct and its
progressive enhancement dead. These are `Warning`, printed on every management command, exiting 0.

The cost of the error is stated rather than hidden: AI-Shipping-Labs cannot start against this
package until it adds the adapter above. That is the point. Its mounted public unsubscribe page
serves 21kB of chrome and no form today, and the fix is one file. The same reasoning was applied to
the Studio shell in community-base#279 and produced `community_base.studio.E001`.

Note for the owner: `.github/workflows/cross-repo-check.yml` runs `uv run python manage.py check`
against the in-progress package as a hard step, so the AI-Shipping-Labs job of that workflow goes
red on this branch and stays red until AISL ships its adapter. This is the check working, not a
regression, but it is a red CI the owner did not have before, and it is why C7.25a and C7.25b exist
as site issues.

## Why the check walks the template tree instead of rendering a probe

`community_base/studio/checks.py` answers a narrower version of this question by rendering two
probe templates and looking for a sentinel, and that is right there: the template it probes,
`community_base/studio/base.html`, is a package template whose replacement is a package-shaped
shell, safe to render with an empty context.

`base.html` is not that. It is arbitrary site chrome: AISL's is 530 lines with custom template
tags, structured-data emission and context processors, and rendering it with an empty context at
`manage.py check` time is neither safe nor meaningful. So this check compiles the chain and reads
the `BlockNode` names out of it without rendering anything. Compiling is still an observation of
the real loader, so a site override of the adapter path is seen exactly as Django sees it.

The two checks sit beside each other rather than one replacing the other. They ask about different
templates, `community_base/public/base.html` and `community_base/studio/base.html`, on behalf of
different page sets, and neither subsumes the other. `community_base.studio.E001` is unchanged.

## What the check deliberately does not report

A package template the site has shadowed with its own copy at the same name. The check resolves
each contracted template through the real loader and skips any whose origin is outside the package,
because a site's own template fills the site's own blocks and the package has no standing to
complain about it. This matters immediately: AISL shadows all three package knowledge-base
templates, so without this the check would report four blocks at AISL instead of the one that is
actually broken.

A template no URLconf mounts. The package cannot know which of its pages a site serves, so an
unreachable block is reported whether or not the page is reachable. This over-reports by
construction and is the safe direction.

Whether the site's own templates honour the site's own base. That is the site's, on the surfaces it
mounts, as `community_base/studio/checks.py` already says for Studio.

| | Bytes | Has a form | Has a `cb-page` |
|---|---|---|---|
| Today's AI-Shipping-Labs | 21066 | no | no |

One consequence found by running it rather than by reading it, and it is the strongest argument
either way on severity. Django's test runner runs system checks before it runs tests, so under
`community_base.kernel.E001` the AI-Shipping-Labs suite does not merely fail, it refuses to start.
That is a bigger cost than "the site cannot boot", and it is the cost of choosing an error. It is
still the right choice: the page is public, it is blank, and the remedy is a three-line file that
this branch has already proved clears the check on that site's real base. What it changes is the
sequencing. A7.4 lands the seam override and the pin bump together, and until it does,
`.github/workflows/cross-repo-check.yml` will be red on its AI-Shipping-Labs job.
