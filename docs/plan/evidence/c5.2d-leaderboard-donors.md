## Leaderboard computation

Rollup and ranking (`_update_enrollment_totals`, `_rank_enrollments`):

- Formula: `Enrollment.total_score = sum(Submission.total_score over the cohort's homeworks)
  + sum(ProjectSubmission.total_score over the cohort's projects)`.
- `_scores_by_enrollment` aggregates with `Sum("total_score")` grouped by `enrollment`;
  enrollments with no submissions contribute 0 through `.get(enrollment.id, 0)`.
- Project contributions exclude `volunteer_review_only=True` placeholder submissions; homework
  contributions have no exclusion.
- Sort key is `(-total_score or 0, enrollment.id)`: descending score, ascending enrollment id as
  the only tie-break. `total_score` null counts as 0.
- Rank 1..N is assigned to every enrollment of the cohort, including ones hidden from display;
  ranking and visibility are independent.
- Results persist with one `bulk_update` of `total_score` and `position_on_leaderboard` for all
  enrollments of the cohort; there is no partial or per-enrollment update path.

Visibility and display-name preferences:

- `Enrollment.display_name` (verbose name "Leaderboard name"): `save()` fills a blank value with
  `generate_random_name()` from `courses/random_names.py` ("adjective famous-person").
- `Enrollment.display_on_leaderboard` (default True): the read model filters
  `course=course, display_on_leaderboard=True`.
- `Enrollment.display_public_profile` (default False): the score breakdown view exposes the
  student object only when set; otherwise the record stays anonymous.
- Read ordering is `Coalesce("position_on_leaderboard", Value(999999))` then `id`, so unranked
  rows sort last; page size is 100 with elided page ranges.
- A viewer whose own visible enrollment is missing from the cached payload triggers a cache
  rebuild (`leaderboard_cache_missing_current_student`), so a hidden-from-cache row never hides
  a student from themselves.
- Serialization carries `id`, `display_name`, `total_score`, `position_on_leaderboard` and
  `passed_projects`: completed-project submissions (project state `COMPLETED`,
  `volunteer_review_only=False`) in project id order, keeping only `passed=True` rows, with
  `medal_index = ((index - 1) % 5) + 1`.

## Complaint model lifecycle

- States: created open (`resolved=False`), then resolved (`resolved=True`, `resolved_at`,
  `resolved_by`). Ordering `["resolved", "-created_at"]` keeps open complaints first.
- Issue types: `learning_in_public`, `homework`, `project`, `other`.
- Creation: a logged-in viewer posts `LeaderboardComplaintForm` (`issue_type`, `description`)
  from an enrollment's score breakdown page; the view core `_save_leaderboard_complaint` sets
  `enrollment` from the URL and `reporter` to `request.user`.
- Resolution: staff resolve from the studio complaints page
  (`resolve_leaderboard_complaint_response`); it sets the three resolve fields with
  `update_fields` and records no further action.
- Resolution never recomputes scores or refreshes the leaderboard; correcting data goes through
  studio score edits or the admin recompute action, which trigger refreshes on their own.
- Listing: complaints grouped per enrollment with open and total counts
  (`complaint_enrollments`, `complaints_grouped_by_enrollment`).

## Enrollment total-score rollups

- Fields: `total_score` (default 0) and `position_on_leaderboard` (nullable) on `Enrollment`;
  both already exist on the package model.
- Written only by `update_leaderboard` (full cohort recompute), after the underlying submission
  scores are already persisted.
- Homework input: `Submission.total_score = questions_score + learning_in_public_score +
  faq_score` (package parity in `coursework/scoring.py` `update_score`).
- Project input: `ProjectSubmission.total_score = project_score + project_faq_score +
  project_learning_in_public_score + peer_review_score + peer_review_learning_in_public_score`
  (package parity in `coursework/review.py`).
- `set_learning_in_public_disabled(enrollment, True)` zeroes `learning_in_public_score` on the
  enrollment's homework submissions and both LIP scores on its project submissions, recomputes
  each affected `total_score` without the LIP components (homework:
  `questions_score + faq_score`; project: `project_score + project_faq_score +
  peer_review_score`), then refreshes the leaderboard inside the same transaction.

## Refresh triggers

Every trigger is an explicit `update_leaderboard(course)` call. There are no signals and no
management commands; a package equivalent must expose exactly these hook points.

| Trigger | Donor call site | Timing |
|---|---|---|
| Homework batch scored | `courses/scoring.py` `_mark_homework_scored`, after the homework is saved with state `SCORED`; then `course.first_homework_scored = True` gates leaderboard display | inside the `score_homework_submissions` transaction |
| Project scored | `courses/project_scoring.py` `_complete_scored_project`, after submissions are updated, evaluation scores replaced and the project saved as `COMPLETED` | inside the `score_project` transaction; the package fires `hooks.project_leaderboard_updater` at the same position (`coursework/review.py:569`) |
| Learning-in-public disabled | `courses/services/enrollment_flags.py` `set_learning_in_public_disabled`, after zeroing scores | inside its `@transaction.atomic` |
| Studio homework score edit | `studio_courses/services.py` `update_homework_submission_from_admin`, only when the recomputed `total_score` changed | inside its transaction |
| Manual recompute | `courses/admin/course.py` action `update_leaderboard_admin` ("Update leaderboard") | no transaction wrapper |

- `update_leaderboard` = `_update_enrollment_totals(course)` plus cache invalidation.
- Cache invalidation deletes `leaderboard:{id}`, `leaderboard_data:{id}`, `leaderboard_yaml:{id}`
  and bumps the version counter `leaderboard_cache_version:{id}`; the page cache key
  `leaderboard:{id}` repopulates with a 3600 s TTL, and the export endpoints
  (`api/views/leaderboard_exports.py`) build versioned per-page keys with a 24 h TTL.
- Note the version-key asymmetry: `_invalidate_leaderboard_caches` bumps the version used by the
  export endpoints but deletes the page key directly; the read model also deletes only the page
  key. A package cache contract must cover both consumers.

## Mapping to community_base.coursework

Maps cleanly to existing package surfaces:

- Rollup targets: `Enrollment.total_score`, `position_on_leaderboard`, `display_name`,
  `display_on_leaderboard`, `display_public_profile`, `disable_learning_in_public` all exist on
  `community_base/curriculum/models.py` `Enrollment`.
- `LeaderboardComplaint` exists field for field in `community_base/coursework/models.py`, with
  `settings.AUTH_USER_MODEL` for `reporter` and `resolved_by`.
- Rollup inputs exist: `Submission.total_score` and `ProjectSubmission.total_score` with
  `volunteer_review_only`.
- Cohort gates exist: `Cohort.first_homework_scored`, `project_passing_score`.
- The project-scoring trigger point exists (`hooks.project_leaderboard_updater`, discard
  default); C5.2d supplies the rollup function behind it.

Missing in the package; each would block part of C5.2d step 1:

- No `coursework/leaderboard.py`: `update_leaderboard`, `_update_enrollment_totals`,
  `_rank_enrollments`, `_scores_by_enrollment` and the cache invalidation are not migrated.
  This is the core deliverable.
- No homework batch scoring service: donor `courses/scoring.py` `score_homework_submissions`
  and `_mark_homework_scored` have no package home, and `CourseworkHooks` has no
  homework-scoring or homework-leaderboard hook. Either migrate the batch scoring service with
  a hook, or expose a `homework_leaderboard_updater` hook for the site service to call.
- No `set_learning_in_public_disabled` equivalent: the flag exists on `Enrollment`, but the
  zero-and-rescore service is not migrated, and it is one of the five refresh triggers.
- No complaint services: creation (`_save_leaderboard_complaint` view core) and resolution
  (`resolve_leaderboard_complaint_response`) live only in donor views and studio; the package
  has the model only.
- No read model: filter, order, paginate, serialize and cache logic is view-owned in the donor
  (`course_leaderboard_data.py`); the package needs a service so the C5.2d views and member
  APIs share one implementation.
- No display-name default: package `Enrollment.save` does not generate a random name and the
  donor `random_names.py` vocabulary is not migrated. Decide: package service taking a
  generator callable, with DTC passing its vocabulary, or a site concern in the enrollment flow.
- Enrollment semantics differ: the package `Enrollment` is soft-deletable (`unenrolled_at`,
  conditional unique on active rows) while the donor has none. The rollup must decide whether
  unenrolled rows keep their score and position; record the choice for A5.1.

Stays a site concern:

- Leaderboard, breakdown and complaint views, URLs, templates, `login_required` and messages.
- Cache backend wiring and the public export endpoints (`api/views/leaderboard_exports.py`);
  member APIs are C5.2d step 4, the URL surface stays in the site.
- Django admin action and studio recompute, rescore and complaint-resolution UIs (C5.2e).
- `first_homework_scored` display gating in member home (`courses/services/member_home.py`).
- `record_event` observability: hook observers configured through `COMMUNITY_BASE`.
