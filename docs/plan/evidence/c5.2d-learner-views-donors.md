## Route contract for the five flows

`surface` `Public courses`, `classification` `preserve`, `host` `courses.datatalks.club`,
`source_revision` `98a235283904b4ef9ad29e196298540756cf1bcc`). The contract carries no per-route
auth field; the auth column below is read from the view code.

|---|---|---|---|---|
| Homework form | `homework` | `/<slug:course_slug>/homework/<slug:homework_slug>` | `courses.views.homework.homework_view` | Public GET; learner POST |
| Project submission | `project` | `/<slug:course_slug>/project/<slug:project_slug>` | `courses.views.project.project_view` | Public GET; authenticated POST |

## Homework form view

`courses/views/homework.py` (`homework_view`) + `homework_context.py`; template
`homework/homework.html`.

- Permission: no decorator. Branches on `request.user.is_authenticated`; anonymous GET and
  anonymous POST both render the disabled anonymous page (no enrollment, no submission).
- Enrollment side effect: `authenticated_homework_context(create_enrollment=request.method ==
  "POST")` -- only an actual POST may `get_or_create` the `Enrollment`; a GET render never
  creates one.
- Context keys (template contract), anonymous: `course`, `course_family`, `homework`,
  `question_answers` (list of `(question, processed_answer)`), `is_authenticated=False`,
  `disabled=True`, `accepting_submissions`, `deadline_passed`, plus navigation keys
  `instructions_url`, `homework_module`, `previous_homework`, `next_homework`.
- Context keys added when authenticated: `submission`, `disable_learning_in_public`; `disabled`
  then reflects `homework.state == OPEN` via `homework_state_context`.
- Services called: `homework_detail_objects` (cohort via `get_cohort_or_404`, homework,
  questions ordered by `id`), `question_answers_for_submission` /
  `process_question_options` (`homework_answers.py`), `handle_homework_post`
  (`homework_post_preview.py`) which guards `state != OPEN` with `record_event(
  "homework.submission_rejected", reason: "closed")` and then runs
  `process_homework_submission` inside `transaction.atomic()`.
- Submission side effects in `homework_submission.py`: `Submission` create/update with
  `submitted_at`, `Answer.objects.update_or_create` per `answer_<id>` POST field, datamailer
  sync (`sync_homework_submission_to_datamailer`), confirmation email
  (`send_homework_confirmation_email` with `build_homework_update_url`).

## Project submission view

`courses/views/project.py` (`project_view`) + `project_page_context.py`; template
`projects/project.html`.

- Permission: GET public; POST requires `request.user.is_authenticated`, else error message and
  redirect back to the project page (`project_login_required_response`).
- Closed gate: `project_accepting_submissions` (`state == COLLECTING_SUBMISSIONS`); a closed
  POST re-renders with an error message instead of saving.
- Context keys (template contract): `course`, `course_family`, `project`, `submission`,
  `has_submission`, `is_authenticated`, `disabled`, `accepting_submissions`,
  `certificate_name`, `disable_learning_in_public`.
- `certificate_name` resolution: `user.certificate_name` first, then
  `enrollment.display_name`; the authenticated branch `get_or_create`s the `Enrollment` on GET.
- `submission` lookup excludes volunteer placeholders (`volunteer_review_only=False`), first by
  default ordering.
- Services called: `project_submit_post` (create or update `ProjectSubmission`, applies
  submission and optional fields, learning-in-public links, updates the user certificate name),
  `project_delete_submission`, `record_event("project.validation_failed", ...)` on
  `ValidationError`; success and delete paths redirect with a message.

## Peer review views

List: `courses/views/project_eval.py` (`projects_eval_view`); template `projects/eval.html`.

- Permission: public GET; anonymous context is reduced to `course`, `course_family`,
  `project`, `is_authenticated=False`, `eval_closed` where
  `eval_closed = project.state != PEER_REVIEWING`.
- Authenticated context (`student_project_eval_context`): `reviews` (this learner's
  `PeerReview` rows as reviewer-submission across the project, ordered `optional`),
  `assigned_reviews`, `selected_reviews` (split by `review.optional` via
  `split_project_eval_reviews`), `number_of_completed_evaluation` (count of assigned reviews in
  `SUBMITTED`), `has_submission`, `eval_closed`, plus `course`, `course_family`, `project`,
  `is_authenticated=True`.

Submit: `courses/views/project_eval_submit.py` (`projects_eval_submit`); template
`projects/eval_submit.html`.

- Permission: `@login_required`; then ownership check `review.reviewer.student ==
  request.user`, violation records `project.review_unauthorized` and redirects to the eval list
  with an error message.
- Vote action: `form_action == "vote"` delegates to `update_project_vote` (`courses/votes.py`)
  and redirects back; no state gate.
- Review action: closed gate `project.state != PEER_REVIEWING` re-renders with an error;
  otherwise `project_eval_post_submission` (`project_eval_submit_save.py`) validates criteria
  answers, saves `CriteriaResponse` rows, applies learning-in-public links and time spent, and
  sets `review.state = SUBMITTED`; `ProjectCriteriaValidationError` answers 400, `ValidationError`
  re-renders with messages.
- Context keys (template contract): `course`, `course_family`, `project`, `review`,
  `submission` (under evaluation), `criteria_response_pairs`, `accepting_submissions`,
  `disabled`, `disable_learning_in_public`, `voted_submission_ids`,
  `vote_limit_reached`, `project_votes_per_project` (`PROJECT_VOTES_PER_PROJECT = 3`).
- Services called: `criteria_for_project`, `project_eval_submit_context`
  (`project_eval_submit_context.py`, which also `get_or_create`s the caller's `Enrollment`),
  `get_voted_submission_ids`, `get_project_vote_counts`, `record_event` observability.

## Leaderboard views

`courses/views/course_leaderboard.py` + `course_leaderboard_data.py`; template
`courses/leaderboard.html`.

- Permission: public. Personalization only when authenticated and enrolled:
  `current_student_leaderboard_enrollment` loads the caller's `Enrollment`.
- Context keys (template contract): `enrollments` (serialized dicts, one page),
  `page_obj`, `page_range`, `total_enrollments`, `course`, `course_family`,
  `current_student_enrollment`, `current_student_enrollment_id`, `current_student_page_number`.
- Row shape from `serialize_leaderboard_enrollment`: `id`, `display_name`, `total_score`,
  `position_on_leaderboard`, `passed_projects` (list of `title`, `slug`, `attempt`,
  `medal_index`).
- Services and caching: `get_leaderboard_data` caches the serialized list under
  `leaderboard:<course_id>` for 3600 s; a version key `leaderboard_cache_version:<course_id>`
  and `invalidate_leaderboard_cache(course_id)` (called by enrollment toggles and scoring)
  force rebuilds; `build_leaderboard_data` filters `display_on_leaderboard=True`, prefetches
  completed project submissions (`COMPLETED`, `volunteer_review_only=False`), orders by
  `Coalesce(position_on_leaderboard, 999999)`, then `id`; `Paginator` page size 100 with
  elided page range; the cache is rebuilt when the current student would be missing from it.
- Breakdown (`leaderboard_score_breakdown_view`): template
  `courses/leaderboard_score_breakdown.html`; context `enrollment`, `public_profile` (the
  student only when `display_public_profile`), `show_public_profile_settings_link`,
  `submissions` (homework submissions ordered scored, open, closed), `project_submissions`
  (non-volunteer, by project id).
- Complaint (`leaderboard_complaint_view`, `@login_required`): form `LeaderboardComplaintForm`
  saving `LeaderboardComplaint` with `enrollment` and `reporter`; template
  `courses/leaderboard_complaint.html`; context `enrollment`, `course`, `course_family`,
  `form`; success redirects to the breakdown page.

## Certificate flow

There is no dedicated certificate page and no certificate model row in the donor.

- Storage: `Enrollment.certificate_url` (`CharField`, nullable) and
  `Enrollment.certificate_name` on `courses/models/cohort.py`; the profile-level
  `User.certificate_name` feeds the name used across certificates.
- Issuance trigger: an external certificate pipeline calls
  `POST /api/courses/<slug:course_slug>/certificates`
  (`api_course_certificates`, `bulk_update_enrollment_certificates_view`) with a staff token.
  The payload is `{"certificates": [{"email": ..., "certificate_path": ...}]}` or a bare array.
  `process_certificate_updates` resolves the account identity by normalized email
  (`resolve_accounts_by_email`), rejects unknown/ambiguous identities and non-enrolled users
  with per-item error codes (`user_not_found`, `not_enrolled`, `identity_unavailable`,
  `identity_ambiguous`), then persists `enrollment.certificate_url`.
- Notification: when an enrollment gains a non-empty `certificate_url` for the first time
  (`should_notify_certificate_available`), the batch queues
  `send_certificate_availability_notification` (datamailer email).
- Learner surfaces, all reading `Enrollment.certificate_url`: the enrollment page
  (`courses/enrollment.html` links the certificate when set; the same form edits
  `certificate_name` via `EnrollmentForm`), the course page
  (`course.html` renders a "Download Certificate" button from the `certificate_url` context
  key), and the signed-in member home finished-course cards
  (`templates/core/_member_home_finished.html`, `card.certificate_url` built by
  `courses/services/member_home.py::_finished_cohort_card`, gated on
  `cohort.first_homework_scored`).
- The course dashboard counts graduates as enrollments with a non-empty `certificate_url`.

## Member API surface in the donor

The donor has no member (self) API: nothing under `/api/` serves the signed-in learner's own
flow data by session. `api/urls.py` is a token-authenticated compatibility/operator surface
(`accounts.auth.token_required` on every view; mutations additionally gated by
`api.safety.require_staff_token`). Flow by flow:

| Flow | Donor JSON/YAML endpoint | Method and auth | Payload |
|---|---|---|---|
| Homework form | none for submitting; reads only: `/api/courses/<slug>/homeworks/`, `.../<int:homework_id>/`, `.../by-slug/<slug>/` | GET any token; POST create staff only | `{"homeworks": [...]}` list, detail object; fields from `homework_to_dict` |
| Homework scoring | `/api/courses/<slug>/homeworks/<int:id>/score/` | POST staff | `{"status", "message", "homework_id", "homework_slug", "state", "submissions_count", "rescored_submissions_count"}` |
| Project submission | none for submitting; reads only: `/api/courses/<slug>/projects/`, detail, `by-slug` | GET any token; POST create staff only | list/detail dicts from `project_to_dict` |
| Peer review | `/api/courses/<slug>/projects/<int:id>/assign-reviews/` (and by-slug) | POST staff | assignment result; no learner review-submission endpoint |
| Leaderboard | `/api/courses/<slug>/leaderboard.yaml` | GET public, no token | YAML: full leaderboard with per-homework and per-project breakdowns, paginated, cached 24 h with the version key |
| Certificate | `/api/courses/<slug>/certificates` | POST staff | request `{"certificates": [{"email", "certificate_path"}]}`; response `{"success", "updated_count", "error_count", "updated", "errors"}` |
| Exports | `/api/courses/<slug>/homeworks/<slug>/submissions`, `.../projects/<slug>/submissions`, `.../graduates` | GET (export views) | YAML/JSON export data for operators |
| Enrollment toggles (learner JSON) | `update_enrollment_toggle` on the courses urlconf | POST, `@login_required @require_POST`, session | request `field` in `{display_on_leaderboard, display_public_profile}`, `value`; response `{"field", "value"}` or 400 `{"error": ...}`; invalidates the leaderboard cache |

Conclusion for the mapping: the five learner flows have no donor member-API equivalent to
preserve; the donor learner surface is HTML plus the one enrollment-toggle JSON action. The
donor's `api/` surface is operator-facing and already covered by the compatibility API issues.

## Mapping to package conventions

- Services first: the C5.2c services in `community_base/coursework/` are exactly what the
  learner views must call -- `projects.submit_project`, `projects.delete_project_submission`,
  `review.submit_peer_review`, `review.validate_project_criteria_answers`,
  `review.save_project_criteria_responses`, `review.add_volunteer_peer_review`,
  `review.remove_volunteer_peer_review`, `review.ensure_volunteer_reviewer_submission`,
  `votes.update_project_vote`, `votes.get_voted_submission_ids`,
  `votes.get_project_vote_counts`, `review.score_project`. C5.2d adds the leaderboard rollup
  service behind `hooks.project_leaderboard_updater` and the homework submission service.
- Models: `coursework.models` already holds `Homework`, `Question`, `Submission`, `Answer`,
  `Project`, `ProjectSubmission`, `PeerReview`, `CriteriaResponse`, `LeaderboardComplaint`;
  `curriculum.models.Enrollment` already carries the donor leaderboard and certificate fields
  (`display_name`, `display_on_leaderboard`, `display_public_profile`,
  `position_on_leaderboard`, `total_score`, `certificate_name`, `certificate_url`,
  `disable_learning_in_public`).
- Certificate storage delta: the donor stores only `Enrollment.certificate_url`; the package
  additionally has `curriculum.models.Certificate` (UUID pk, `OneToOne` enrollment, `url`,
  `issued_at`, `hash`, `get_absolute_url` -> `/certificates/<pk>`). C5.2d decides the page view
  serves `Certificate` (or the enrollment field during migration) and records the choice; the
  external award call maps to a package service plus hook, not to a public learner route.
- View style: package function-based views per `community_base/onboarding/views.py` and
  `community_base/community/views.py` -- plain functions, `@login_required` only where the
  donor has it, `@never_cache` on authenticated pages, `render` with package templates, URL
  names prefixed `community_base_*` in an app-level `urls.py`. Donor context keys above are the
  template contract; package templates live under `community_base/coursework/templates/` and
  site templates extend or override them.
- Route identity: the donor's cohort-slug resolution (`get_cohort_or_404`) becomes a package
  helper resolving `course_slug` + cohort identifier to `curriculum.Cohort`; the concrete URL
  patterns (one-segment, two-segment, `cohorts/` namespace) stay in each site's urlconf, which
  mounts the package views -- the package fixes view signatures and names, not site paths.
- Member APIs: register per `community_base/api/README.md` with `@route(...,
  authentication="session", scope=None)` in a `coursework` API module imported from the app
  config (the pattern of `accounts/apps.py` importing `self_api`), mounted by sites under
  `/api/v1/` through `registry.urlpatterns()`. Suggested member surface: `GET/POST`
  `courses/<course_slug>/homeworks/<homework_slug>/submission` (form read/submit),
  `projects/<project_slug>/submission` (submit/delete), `projects/<project_slug>/reviews` and
  `.../reviews/<review_id>` (list/submit), `courses/<course_slug>/leaderboard` (read, paginate
  with `safety.parse_pagination`), `courses/<course_slug>/certificate` (read). Bodies via
  `safety.read_json_object`, errors via `APIError`, mutations keep CSRF through the session
  dispatcher; revision-guarded writes use `requires_if_match=True` like `PATCH me/profile`.
- Stays a site concern: templates and branding (donor `homework/homework.html`,
  `projects/project.html`, `projects/eval.html`, `projects/eval_submit.html`,
  `courses/leaderboard*.html`, `courses/enrollment.html` stay in `dtc-website`, adapted to the
  package template contract), the URL paths and route aliases, datamailer confirmation and
  certificate emails (wire through coursework hooks and Relay), `record_event` observability
  (hook payloads per C5.2c), and the certificate pipeline endpoint, which is operator-facing
  and belongs to the site's compatibility API, not to the member API.
