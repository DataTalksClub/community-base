## Leaderboard rollup (`update_leaderboard`)

- Totals: `Sum("total_score")` grouped by enrollment over `Submission` rows filtered by
  `homework__course`, plus the same over non-volunteer `ProjectSubmission` rows. Missing
  entries count 0. `Enrollment.total_score` is homework + project.
- Ranking: sort key `(-total_score, enrollment.id)`, positions 1-based, ties broken by
  enrollment id. `bulk_update` covers exactly `total_score`, `position_on_leaderboard`.
- Cache invalidation deletes `leaderboard:{course.id}`, `leaderboard_data:{course.id}`,
  `leaderboard_yaml:{course.id}` and increments `leaderboard_cache_version:{course.id}`.
- Logs started/duration at info level.
- Callers: homework scoring (`courses/scoring.py:111`, inside the scoring transaction),
  project scoring (`courses/project_scoring.py:110`, inside the scoring transaction; the
  package already fires this position as the `project_leaderboard_updater` hook),
  `set_learning_in_public_disabled`, admin actions (`courses/admin/course.py:80`) and studio
  rescoring (`studio_courses/services.py:26`; C5.2e surfaces).

Display surface (`courses/views/course_leaderboard_data.py`):

- `LEADERBOARD_PAGE_SIZE = 100`, Django `Paginator` with elided page range.
- Rows: `Enrollment.objects.filter(display_on_leaderboard=True)` ordered by
  `Coalesce("position_on_leaderboard", 999999), id`, serialized to dicts
  `{id, display_name, total_score, position_on_leaderboard, passed_projects}` where each
  passed project carries `{title, slug, attempt, medal_index}` and
  `medal_index = ((attempt - 1) % 5) + 1` (five attempts per medal is a hardcoded site
  constant).
- Cached under `leaderboard:{course.id}` for 3600 s; rebuilt when the current student is
  missing from the cached page set (`leaderboard_cache_missing_current_student`).
- The viewer's own enrollment id and page number are computed for "find me" navigation.
- The view-layer cache and its serialization are presentation; the package service owns the
  rollup and ranking and exposes invalidation, sites keep their cache policy.

## Homework scoring service (`score_homework_submissions`)

- Signature `(homework_id, force=False) -> (HomeworkScoringStatus, message)` with
  `HomeworkScoringStatus.OK | FAIL`, run inside one `transaction.atomic()`.
- Preconditions, in order, each returning `(FAIL, message)` without raising:
  `due_date > now` ("update the due date"); state `CLOSED` ("update the state to OPEN");
  state `SCORED` and not `force` ("already scored").
- Events: `homework.scoring_started` before the checks; `homework.scoring_failed` with the
  reason; `homework.scored` with `duration_ms`.
- Batch: submissions `select_related("enrollment")`, all answers
  `select_related("question", "submission")`, grouped by submission id, per-submission
  `update_score(submission, answers, save=False)` (already in the package from C5.2b).
- Persistence: `bulk_update` on submissions covers `questions_score`,
  `learning_in_public_score`, `faq_score`, `total_score`; `bulk_update` on answers covers
  `is_correct`.
- Then: state becomes `SCORED`, `update_leaderboard(course)`, `course.first_homework_scored
  = True` saved, `calculate_homework_statistics(homework, force=True)` (package has the
  statistics service from C5.2b).
- Callers today: admin action and studio rescore views (C5.2e surfaces); the service itself
  is this issue's scope.

## Visibility preferences (`set_learning_in_public_disabled`)

- `Enrollment.disable_learning_in_public = disabled` saved with `update_fields`, inside
  `transaction.atomic()`.
- When disabling: homework submissions get `learning_in_public_score = 0` and
  `total_score = questions_score + faq_score`; project submissions get
  `project_learning_in_public_score = 0`, `peer_review_learning_in_public_score = 0` and
  `total_score = project_score + project_faq_score + peer_review_score`; both via
  `bulk_update`, skipping rows already at zero.
- Always ends with `update_leaderboard(enrollment.course)` inside the transaction.
- Display-name and visibility fields (`display_name`, `display_on_leaderboard`,
  `display_public_profile`, `certificate_name` with user sync) are edited by
  `EnrollmentForm` on the enrollment page (`courses/views/course_enrollment.py`); that page
  is the step 1 "display-name and visibility preferences" surface alongside the leaderboard
  opt-outs.

## Registration campaign services

Bindings (`courses/services/registration_campaigns.py`):

- `campaign_slug_in_registration_url`: parses CMP-style `https://<host>/register/<slug>/`
  with a regex; host unconstrained; returns `""` when the URL is not a campaign path.
- `active_campaign_for_cohort`: the active campaign whose `current_course` is this exact
  cohort, lowest id first.
- `next_edition_campaign_for_cohort`: for a closed edition, the active campaign named by the
  cohort's `registration_url` slug, excluding one that already promotes this cohort.
- `family_registration(course)`: over visible editions ordered `(-year, -id)`, the first
  edition with an active promoting campaign wins (campaign + cohort); otherwise the first
  next-edition campaign returns campaign only; else nothing. A family with no campaign
  offers no registration.

State transitions (both fail closed with `RegistrationCampaignStateError`):

- `stop_registration(campaign)`: row-locked; requires `current_course` set; clears it;
  writes audit event `courses.registration_campaign.registration_stopped` with the change
  and metadata.
- `open_new_cohort(campaign, cohort)`: row-locked; requires `current_course` empty; sets it;
  writes audit event `courses.registration_campaign.cohort_opened`.
- Donor audit writes go through `core.audit` (`AuditWriteContext`, `record_audit_event`);
  that is a site kernel concern. The package services keep the state machine and expose
  success/failure to callers; audit stays site-side.

## Registration counts (campaign count semantics)

From `courses/services/registration_counts.py`, matching spec 04:

- The public count is always `registration_baseline_count + count(native CourseRegistration
  rows for the campaign's current cohort)`, computed live.
- The baseline applies only while `registration_baseline_cohort` names the campaign's
  current cohort; a baseline recorded for a previous edition never carries onto a new one.
- `registration_native_start_at` excludes rows created before that instant, so pre-import
  rows never double-count the baseline.
- Returns `None` when the campaign has no current cohort: nothing is counted once a campaign
  stops promoting a specific edition.
- The package model already carries the three baseline fields; the package renames
  `current_course` to `current_cohort` (same rename pattern as `Project.course` to
  `cohort`).

## Learner views

All in-scope routes live under `/courses/` and accept GET and POST with `request.method`
dispatch (no method decorators). Course/cohort resolution is
`get_cohort_or_404(course_slug, cohort_year=None)` resolving `Cohort` by course slug plus
`identifier` (or by cohort slug when the second segment is absent). Absolute URLs for emails
prefer `settings.PUBLIC_BASE_URL`, then the request host, then the first concrete
`ALLOWED_HOSTS` entry. The only auth decorator in scope is `@login_required` (eval add,
eval delete, eval submit, leaderboard complaint); everything else is manual
`is_authenticated` checks or anonymous-allowed.

### Homework flow

- `homework_view` (`homework` / `cohort_homework` routes): anonymous GET renders read-only;
  an anonymous POST also renders read-only; only an authenticated POST may create the
  `Enrollment` (`get_or_create`) and submit. POST pipeline:
  `handle_homework_post` -> state check (`HomeworkState.OPEN` else
  `record_event("homework.submission_rejected", reason "closed")` + `messages.error` +
  redirect) -> `process_homework_submission` in `transaction.atomic()`:
  parse `answer_<id>` POST lists, update `submitted_at` on the existing `Submission` or
  create `Enrollment` + `Submission`, `update_or_create` one `Answer` per question, apply
  `homework_link`, learning-in-public links (duplicate links across the user's course raise
  `ValidationError`), time spent (non-numeric raises), `problems_comments`,
  `faq_contribution_url` (GitHub issue/PR allowlist validator), `full_clean`, `save`;
  then `record_event("homework.submitted", ...)`; then two `transaction.on_commit`
  callbacks: confirmation email and datamailer membership sync; then
  `messages.success` + redirect to the homework page. `ValidationError` fires
  `homework.validation_failed` and re-renders with echoed POST values.
- `homework_statistics` (`homework_statistics` route): anonymous allowed; unscored homework
  redirects with `messages.error`; computes and persists
  `calculate_homework_statistics(homework, force=False)` plus per-question stats; renders
  `homework/stats.html`.
- `homework_submissions` (`homework_submissions` route): staff-only redirect to the studio
  route (gate: studio access plus group `site_admin` or `course_operator`); C5.2e surface.
- Template: `homework/homework.html` with partial `_submission_form.html`.

### Project submission flow

- `project_view` (`project` route): GET builds context (note: GET creates the `Enrollment`
  via `get_or_create`, unlike homework) and renders `projects/project.html`; POST:
  anonymous -> error message + redirect (not to login); state must be
  `COLLECTING_SUBMISSIONS` else "submission form is closed"; `action == "delete"` deletes
  the user's non-volunteer submission and fires `project.deleted`; otherwise create or
  update (detected via existing non-volunteer submission), write `User.certificate_name`
  from POST, apply `github_link`, `commit_id`, optional learning-in-public links, time
  spent, `problems_comments`, `faq_contribution_url` (GitHub allowlist), `full_clean`,
  `save`, fire `project.submitted` / `project.validation_failed`, schedule the confirmation
  email and datamailer sync `on_commit`, `messages.success`, redirect.
- `projects_list_view` (`project_list` route): GET lists non-volunteer submissions
  (`select_related("enrollment")`, `vote_count` annotation, ordered `-project_score` when
  `COMPLETED` else `-submitted_at`, page size 25), decorated with `to_evaluate`, `own`,
  `vote_limit_reached` and assigned-review grouping; renders `projects/list.html`. POST
  votes: anonymous redirects to `login`; otherwise `update_project_vote` (C5.2c service); an
  `XMLHttpRequest` header gets a JSON response `{submission_id, vote_count, voted,
  voted_submission_ids, votes_left, vote_limit_reached}`, others redirect. No events here.
- `project_submissions` (`project_submissions` route): staff redirect to studio, C5.2e.
- `project_results` (`project_results` route): anonymous allowed; own submission, evaluation
  scores in `criteria_for_project` order, per-option vote tallies from submitted reviews,
  free-text `note_to_peer` feedback; renders `projects/results.html`. Read-only.
- `project_statistics` (`project_statistics` route): requires `COMPLETED` else redirect
  with message; computes and persists project statistics; renders `projects/stats.html`.

### Peer review flow

- `projects_eval_view` (`projects_eval` route): anonymous allowed (`eval_closed` when state
  is not `PEER_REVIEWING`); authenticated context reads own submissions (including
  volunteer) and `PeerReview` rows where the reviewer is one of them, split into assigned
  (non-optional) and selected (optional) with a completed count; renders
  `projects/eval.html`.
- `projects_eval_add` (`projects_eval_add` route, `@login_required`): resolves the caller's
  real submission or creates the volunteer one (`Enrollment.get_or_create`, then
  `ProjectSubmission.get_or_create` with `volunteer_review_only=True` and site defaults
  `github_link="https://github.com/DataTalksClub/course-management-platform"`,
  `commit_id="volunteer"` — the package service takes these defaults as arguments, done in
  C5.2c), `get_or_create`s the optional `PeerReview` (skipping own submissions), fires
  `project.optional_review_added` with `created`, redirects to `project_list`.
- `projects_eval_delete` (`projects_eval_delete` route, `@login_required`): 404 without own
  submission; deletes only own `optional=True` review; fires `project.optional_review_deleted`
  when deleted; redirects to `projects_eval`.
- `projects_eval_submit` (`projects_eval_submit` route, `@login_required`): ownership check
  (`review.reviewer.student != user` fires `project.review_unauthorized` with an error
  message and redirect); GET renders `projects/eval_submit.html` with criteria pairs
  annotated with selection state (GET creates the `Enrollment`), vote context, accepting/
  disabled flags; POST dispatch: `form_action == "vote"` votes and fires
  `project.vote_updated`; closed state rejects; otherwise validates posted criteria ids
  belong to the project (stray ids are a `HttpResponseBadRequest`), then in one
  transaction: `update_or_create` one `CriteriaResponse` per criteria, learning-in-public
  links capped by `learning_in_public_cap_review`, `time_spent_reviewing`,
  `problems_comments`, `note_to_peer`, `submitted_at`, state `SUBMITTED`; fires
  `project.review_submitted`; success message; redirect to `projects_eval`. No emails.
- Template family: `projects/_base.html`, `eval.html`, `eval_submit.html`, `list.html`,
  `list_all.html`, `project.html`, `results.html`, `stats.html`.

### Leaderboard views

- `leaderboard_view` (`leaderboard` two-segment and family routes plus `cohort_leaderboard`):
  anonymous allowed, read-only, paginated; renders `courses/leaderboard.html`.
- `leaderboard_score_breakdown_view` (`leaderboard_score_breakdown` route): anonymous
  allowed (route is privacy-tagged noindex); resolves the enrollment by id within the
  course; shows homework submissions ordered by state (SCORED, OPEN, CLOSED) and
  non-volunteer project submissions; exposes the student identity only when
  `display_public_profile`; renders `courses/leaderboard_score_breakdown.html`.
- `leaderboard_complaint_view` (`leaderboard_complaint` route, `@login_required`): GET
  renders `LeaderboardComplaintForm` (`issue_type`, `description`); POST saves with
  `enrollment` and `reporter=request.user`, success message, redirect to the breakdown
  page; renders `courses/leaderboard_complaint.html` on invalid POST. No events.

### Certificate surface (donor reality)

There is no certificate learner view in `courses/views/`. The certificate artifact is
`Enrollment.certificate_url`, ingested by the `api` app
(`api/views/enrollment_certificate_updates.py`, `enrollment_certificate_delivery.py`) with
the "certificate available" email sent by datamailer. Learner-facing certificate touch
points are: `certificate_name` capture on the project form and registration, the
`EnrollmentForm` certificate-name sync, the dashboard listing enrollments with
`certificate_url`, and `certificate_url` in the course page context. The C5.2d "certificate
page" is therefore a package page rendering an enrollment's certificate from
`Enrollment.certificate_url` (issued-at/hash fields per C5.1a), with issuance itself
remaining an ingested/staff flow, not a learner flow.

### Registration flow

- `registration_campaign_view` (`registration_campaign` route, `register/<slug:campaign_slug>/`;
  production canonical `https://datatalks.club/register/<slug>` rendered as a canonical
  link): the campaign must be active (`get_object_or_404` on slug + `is_active`).
- Account gate: anonymous plus `settings.REGISTRATION_REQUIRES_ACCOUNT` (default True)
  renders a marketing-only page on GET and redirects anonymous POST to
  `login?next=<path>`; no anonymous rows.
- Authenticated (or un-gated) POST: `CourseRegistrationForm` (fields `email`, `name`,
  `company_name`, `country`, `role`, `comment`, `accepted_newsletter`; newsletter consent
  required with site-branded label; country validated against the region map; email
  disabled and prefilled when authenticated; duplicate email per campaign rejected via
  `email_normalized` match) -> `form.save()` (sets `campaign`, `course` = campaign's
  current cohort, `region`, `user`/`email`) -> `update_user_profile_from_registration`
  maps `name` to `User.certificate_name`, `country`, `region`, `registration_role`, saving
  only changed non-empty values -> two `transaction.on_commit` callbacks (datamailer
  contact/membership sync and confirmation email) -> `record_event("registration.submitted",
  ...)` -> always re-renders `courses/register.html` (with success block on valid POST).
- Duplicate handling `_existing_user_registration` matches `Q(user) | Q(email_normalized)`.
- Context includes `signup_count` from `public_course_registration_count`,
  `course_is_open` (the cohort has any homework or project rows), markdown-rendered
  `marketing_html`, `video_embed_url`, `start_course_url`, country options, gate and
  profile-identity fields.

  hook, sites keep their cache scheme.
- The medal grouping constant (5 attempts per medal) and `PROJECT_VOTES_PER_PROJECT = 3`

- The dual route registration (two-segment cohort, one-segment family, `cohorts/` alias) and

  contract registers one canonical shape per route name and sites layer their aliases.

## Spec 04 constraints (`_docs/specs/04-courses-and-cohorts.md`)

- "Registration count" (lines 242-256) states exactly the semantics implemented in
  `registration_counts.py` (recorded above) and adds: the copied registration template stays
  byte-identical; the only copied-view seam is this one query.
- "Registration" (lines 188-240) points at a target flow beyond the current donor view: one
  verified durable account plus a completed member-confirmed profile, a resumable four-step
  flow (account ownership, shared profile, course-specific step, confirmation), no anonymous
  `CourseRegistration` before verification, immutable target cohort snapshot, uniqueness by
  cohort plus normalized email, campaign repointing never rewrites history, minimized
  shared-profile snapshot rules, and Relay-owned delivery through an approved sender. The
  donor view implemented today is the simpler gate + form; the package ports the donor
  behavior and records the spec as the direction D5.x adopts, not something to build here.
- "Enrollment and certificates" (lines 180-186): enrollment unique by learner and cohort;
  leaderboard name/visibility, certificate name, score rollups, learning-in-public controls
  and timestamps stay cohort-specific; certificate becomes an explicit cohort-scoped record.
- "Preserved learner behavior" (lines 278-286) lists for this issue: homework question
  types, optional fields, create/update submission, answer checks, scoring, answer reveal,
  statistics, FAQ and learning-in-public contributions; project GitHub/commit submission,
  required/volunteer peer review, criteria responses, assignment, voting, scoring, pass/
  fail, results and statistics; cohort leaderboard, breakdown, visibility preferences,
  complaints, graduate export and certificate updates. Privacy tightening must be a
  documented product decision, never hidden in the migration.
- Studio coverage (registration campaign management, leaderboard recompute, complaint
  resolution, certificate bulk issue) is C5.2e; the admin API compatibility routes are the
  adoption milestone's concern.

## Member APIs (donor reality)

The DTC `api/` app is staff, export and webhook oriented; there are no
session-authenticated member APIs for the learner flows. Auth is
`accounts.auth.token_required` (any active account token) plus `api.safety.require_staff_token`
(staff token) for mutations, and `api/auth.py:staff_json_required` (session staff) for
the homework/project/question CRUD.

- Public, no auth: `api_health`, `api_course_criteria_yaml`, `api_course_leaderboard`
  (`courses/<slug>/leaderboard.yaml`, full leaderboard with per-homework and per-project
  breakdowns, 24 h cache sharing the `leaderboard_yaml:{id}` key that
  `update_leaderboard` invalidates), `api_courses_list`, `api_course_detail`.
- Token + staff token (ops/service): `api_course_certificates` (bulk certificate
  ingestion: url, issued-at, revocation), `api_course_graduates` (emails + certificate
  names), `api_registration_campaigns` list/create, detail patch, registrations export
  (campaign management), `api_homework_submissions_export`, `api_project_submissions_export`.
- Session staff (`staff_json_required`): homeworks list/detail/by-slug, score endpoints
  (which call `score_homework_submissions` / `score_project`), projects, questions,
  assign-reviews.
- Webhooks: datamailer events, GitHub course repository, datamailer send-audits.
- The learner-facing surface is entirely server-rendered pages under `/courses/`; the
  package member APIs for the learner flows (step 4) therefore follow the AISL member-API
  shape adopted in C5.1c (`curriculum/api_views.py`), not a DTC donor endpoint.

## AISL note

AISL has no leaderboard, no registration campaigns and no homework scoring display; grep
finds no leaderboard code anywhere in `api/`, `content/` or `website/`. Registration is
purchase/enrollment driven. Certificates are `CourseCertificate` rows
(`content/models/peer_review.py:87`) with project `certificate_issued_at` and revocation
fields, staff-issued through `api/views/course_certificates.py` (already package surface
since C5.1d). The C5.2c AISL mapping (project status to `Project.state`) remains the only
AISL touch point; A5.1 maps `CourseCertificate` with the curriculum surfaces. Nothing in
C5.2d needs an AISL donor port.
