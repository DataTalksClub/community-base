## RegistrationCampaign lifecycle

- No campaign types exist. There is one reusable campaign model; a campaign is the
  marketing definition that outlives editions, not a per-run object.
- A cohort reaches its campaign through one of two bindings, both published by CMP:
  `current_course` means "register for this edition now"; `Cohort.registration_url`
  (`https://courses.datatalks.club/register/<campaign-slug>/`) means "this course
  registers here" and outlives `current_course`.
- Nothing is derived: a registration URL that is not a campaign path, or names an
  unknown campaign, resolves to no registration at all (`mlops-zoomcamp-2025` must
  stay silent). Slug parsing: `^https?://[^/]+/register/(?P<slug>[a-z0-9](?:[a-z0-9-]*[a-z0-9])?)/?$`.
- State is `current_course`: set means "promoting one cohort"; `None` means
  "future/none", waiting for the next edition. `is_active` gates page and selection;
  selection picks the lowest-id active campaign (`active_campaign_for_cohort`,
  `next_edition_campaign_for_cohort`).
- Transitions exist only as services, both fail closed under a row lock:
  `stop_registration` requires an open cohort and sets `current_course=None`;
  `open_new_cohort` is valid only from the `None` state and never silently repoints
  an open campaign. Both record an `AuditEvent`
  (`courses.registration_campaign.registration_stopped` / `.cohort_opened`) with
  before/after `current_course_id`.
- Rotation semantics: repointing never rewrites historical registrations, and a
  baseline recorded for a previous edition never carries onto the new one.
- Date semantics: the campaign has only `created_at`/`updated_at`; no window dates.
  Openness is derived: `campaign_course_is_open` is true when the current cohort has
  any `Homework` or `Project` rows. Cohort classification (finished/upcoming/active)
  uses `finished`, `registration_url`, `start_date` and today's date; there is no
  state column.

## CourseRegistration semantics

- Uniqueness: `unique_together ["campaign", "email_normalized"]`; the same person can
  register for a later cohort through the same campaign.
- `email_normalized` is derived in `save()` (strip + lower). The form validates the
  duplicate per campaign and reports "You have already registered for this course."
- `course` defaults to `campaign.current_course` inside `save()`, so the row
  snapshots the cohort being promoted at registration time; later repointing never
  moves existing rows.
- Creation is account-owned: with `REGISTRATION_REQUIRES_ACCOUNT` (default on) an
  anonymous GET sees the campaign plus count and a sign-in gate, and an anonymous POST
  redirects to login, so no anonymous row is ever created. Spec 04 tightens this
  further (verified durable account plus completed member-confirmed profile) as the
  target flow.
- Authenticated saves force `email` to the account email, set `user`, and update the
  user profile from the registration. Existing-registration lookup matches
  `user` OR `email_normalized`.
- Cancellation: no learner-facing cancel. Admin deletion is the only removal path and
  fires `post_delete` to remove the datamailer recipient; because the public count is
  a live aggregate, deletion lowers it.
- No status or state field: a row is a registration. Newsletter consent is currently
  required (`accepted_newsletter=True` enforced by the form); spec 04 makes new
  consent separate and optional while preserving historical evidence as migration
  input.

## Spec 04 count semantics

Spec section "Registration count" (`_docs/specs/04-courses-and-cohorts.md`) and its
implementation `courses/services/registration_counts.py`:

- Baseline count: `registration_baseline_count` is a fixed historical figure recorded
  once, for registrations that happened before this database had `CourseRegistration`
  rows for the campaign (e.g. a legacy CMP export). Zero when there is nothing to
  backfill. Nothing tracks who changed it, when, or why.
- Native boundary: `registration_native_start_at` is the instant native
  `CourseRegistration` rows became the complete record. Rows created before that
  instant would double-count the baseline, so they are excluded; unset when there is
  no baseline to protect.
- Current cohort: `registration_baseline_cohort` records which cohort the baseline was
  computed for. The baseline applies only while this names the campaign's current
  cohort (`current_course`); the moment the campaign promotes a different cohort, the
  baseline stops applying entirely. The count is specific to both the campaign and the
  current cohort.
- The exact computation, verbatim from `public_course_registration_count`:

```python
cohort = campaign.current_course
if cohort is None:
    return None
baseline_count = 0
native_start_at = None
if campaign.registration_baseline_cohort_id == cohort.id:
    baseline_count = campaign.registration_baseline_count
    native_start_at = campaign.registration_native_start_at
native_rows = CourseRegistration.objects.filter(campaign=campaign, course=cohort)
if native_start_at is not None:
    native_rows = native_rows.filter(created_at__gte=native_start_at)
return PublicCourseRegistrationCount(count=baseline_count + native_rows.count())
```

- Result: `baseline (when it still applies) + count(native rows created at or after
  the native boundary, for the campaign's current cohort)`; the `__gte` boundary is
  inclusive. `None` only when the campaign has no current cohort; every other campaign
  renders its live total. The count is computed live each call; there is no versioned
  overlay (migration `0002_simplify_registration_counts.py` deleted the former
  `CourseRegistrationCountSlot`/`Revision` tables, copying only genuinely active
  baselines onto the plain fields).

## Mapping to the package models

Field-by-field, `community_base/coursework/models.py` `RegistrationCampaign` and
`CourseRegistration` match the donor. Deltas:

- Donor `RegistrationCampaign.current_course` becomes `current_cohort`; donor
  `CourseRegistration.course` becomes `cohort`. Related names match
  (`registration_campaigns`, `registrations`, `course_registrations`).
- Donor `unique_together` becomes an explicit `UniqueConstraint`
  (`cb_course_registration_campaign_email_uq`); equivalent enforcement.
- Donor `registration_baseline_count` carries `db_default=0`; the package uses
  `default=0` only. Cosmetic.
- `save()` on both models derives `email_normalized` and defaults the cohort from the
  campaign identically.

Package gaps that the implementation must decide on:

- Region derivation has no package counterpart. Donor `region_for_country` reads the
  `courses/countries.txt` catalog (regions plus a Top Countries ordering) and both the
  form validation ("Select a valid country.") and `region` depend on it. The catalog
  is site content: the package service should accept a country-to-region resolver, and
  DTC passes its catalog (same pattern as the C5.2c volunteer submission defaults).
- No package service module exists for campaigns. `stop_registration`,
  `open_new_cohort`, `active_campaign_for_cohort`, `next_edition_campaign_for_cohort`,
  `family_registration` and `public_course_registration_count` need a home
  (`coursework/registration.py`).
- Donor transitions record `AuditEvent` rows through `core.audit` /
  `ServiceContext`; the package has no audit kernel. The established replacement is a
  `coursework/hooks.py` hook (like `project_scored`); audit rows stay a site concern.
- `campaign_course_is_open` needs `Homework`/`Project` existence checks; both models
  already live in the package.
- The sign-in gate, verified-account and member-profile requirements, the shared
  profile snapshot, privacy acknowledgement and separate marketing consent of spec 04
  are identity/account surfaces, not coursework; the package count function and
  registration model do not depend on them.
- The datamailer recipient sync and the confirmation email are site integrations;
  spec 04 routes new email through Relay sender `courses`. Package hooks fire instead;
  DTC wires them.
- Enrollment conversion (registration to `Enrollment`) has no donor service in this
  scope. Package `Enrollment` deliberately differs from the donor (soft delete via
  `unenrolled_at`, unique only among active rows); member-home style "my cohorts" and
  any conversion must use the package semantics.
