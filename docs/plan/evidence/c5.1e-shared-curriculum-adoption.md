# Curriculum ownership adoption: course-owned modules, cohort placement, and #252 nesting

Captured: 2026-09-16. Supersedes the cohort-owned `Module`/`Unit` shape merged in C5.1a-C5.2e
(never tagged; latest package release is `v0.3.9`, predating curriculum entirely). Written in
response to `community-base#253` (curriculum ownership) and `community-base#252` (nesting), and
to the owner's explicit steer during this investigation: design the right shape informed by what
DataTalks.Club learned, do not lift its models or its compatibility scar tissue verbatim, and
optimise for AI Shipping Labs (the priority consumer) over DataTalks.Club's more complex case.
Breaking changes are accepted; this is not a release yet.

Evidence for the ownership-model claim below (DataTalks.Club has already converged on
course-owned curriculum with per-cohort placement) is posted with file/line citations on
`community-base#253`: https://github.com/DataTalksClub/community-base/issues/253#issuecomment-5697834824.
This document does not re-derive that evidence; it uses the one conclusion worth keeping from it
("curriculum belongs to the course; cohorts place it") and designs the package's own shape from
AI Shipping Labs' actual model outward, not from DataTalks.Club's `Shared*` classes.

## 0. What changes and why, in one paragraph

`Module` moves from `cohort` FK to `course` FK: one module tree per course, not one copy per
cohort. `Module.parent` (nullable self-FK, max two levels) adds submodules. `Module.is_bonus`,
`Module.available_after_days`, `Unit.kind`, `Unit.session_position`, `Unit.is_bonus` land in the
same change (`#252`). A cohort sees the full course tree by default, with zero extra rows — this
is AI Shipping Labs' entire requirement. A new optional `CohortModule` placement lets a cohort
curate a subset or a different order of top-level modules, for DataTalks.Club's many-cohorts-
per-course case. `Cohort.curriculum_format` (`legacy`/`modules`) is deleted: there is one shape
now, so the field has no value left to hold.

## 1. AI Shipping Labs' real model, which this design targets directly

Read from `~/git/ai-shipping-labs/content/models/course.py` (the site's actual, currently-live
model, not the future package):

- `Module` (line 318): `course = models.ForeignKey(...)` (line 321) — course-owned, not
  cohort-owned. `sort_order = models.IntegerField(default=0)` (line 326).
- `Unit` (line 374): `module = models.ForeignKey(...)` (line 377), `sort_order` (line 382),
  `available_after_days` (line 417, drip offset) already exists at the unit level.
- One cohort's dates and mode are a thin wrapper (`content/models/cohort.py`); the curriculum
  itself was never cohort-scoped on this site. The package's current `Module.cohort` FK is a
  divergence from AI Shipping Labs' real shape, not a faithful model of it — confirmed
  independently of the DataTalks.Club investigation.

`AI-Shipping-Labs/website#1674` (the site's local, in-flight implementation of `#252`, since the
site cannot consume this package yet) already adds, on top of that real model:
`Module.parent`, `Module.is_bonus`, `Module.available_after_days`; `Unit.kind`,
`Unit.session_position`, `Unit.is_bonus`; `Cohort.mode`. Every field name below matches #1674
exactly, on purpose — see section 7.

## 2. Target shape (`community_base.curriculum`, label `cb_curriculum`)

```
Course
  ---- Module (course FK, parent FK to self, nullable, max depth 2)
         ---- Unit (module FK)
Cohort (course FK, mode: cohort | self_paced, dates, drip base)
  ---- CohortModule (optional; cohort FK, module FK, sort_order) -- placement, not ownership
Enrollment (user, cohort)          -- unchanged
UnitProgress (user, unit, completed_at)  -- unchanged
Certificate (enrollment)           -- unchanged
CurriculumImportRun                -- unchanged
```

### `Module`

| Field | Change | Notes |
|---|---|---|
| `course` | new, replaces `cohort` FK | `models.ForeignKey(Course, on_delete=CASCADE, related_name="modules")` |
| `parent` | new (#252) | `models.ForeignKey("self", null=True, blank=True, on_delete=CASCADE, related_name="children")` |
| `is_bonus` | new (#252) | `models.BooleanField(default=False, db_default=False)` |
| `available_after_days` | new (#252) | `models.IntegerField(null=True, blank=True)`; drip offset for a top-level ("week") module, cascades to its units the same way `Unit.available_after_days` already overrides it |
| `slug`, `title`, `sort_order`, `overview`, `overview_html` | unchanged | |

Constraints, same reasoning AISL's `#1674` already committed to (mixed-content rule spans two
related tables, `children` and `units`, so it is a `clean()` invariant, not a DB
`CheckConstraint`): `parent != self`; `parent.parent_id is None` when `parent` is set (depth cap
of two); `parent.course_id == self.course_id`; a module cannot have both `children` and direct
`units`, checked on every save path and named in the error.

`cb_module_cohort_slug_unique` becomes `cb_module_course_parent_slug_unique` on
`(course, parent, slug)` — slug uniqueness is scoped to siblings under the same parent (or the
top level, `parent=None`), not the whole course. This is what makes the "two submodules under
different parents can each contain `section-overview`" case in the task's quality bar work by
construction.

### `Unit`

| Field | Change | Notes |
|---|---|---|
| `kind` | new (#252) | `models.CharField(max_length=20, choices=[("lesson", "Lesson"), ("homework", "Homework"), ("event", "Event")], default="lesson", db_default="lesson")` |
| `session_position` | new (#252) | `models.PositiveIntegerField(null=True, blank=True)`. No `Unit.event` FK — already settled on `#252` itself (the AISL-divergence comment) and confirmed as final here: a cohort-specific `Event` FK on shared curriculum breaks the moment a second concurrent cohort exists. Resolution by cohort + `session_position` happens at render time, in the site (AISL's `#1674` "Event units resolve by cohort at render time" section is the reference algorithm; DataTalks.Club resolves the same way against its own `EventSeries`-equivalent). The package does not implement the resolution — it has no `events.EventSeries` concept to resolve against on either site identically, and that resolution is inherently a call the site makes over its own cohort/event wiring. |
| `is_bonus` | new (#252) | `models.BooleanField(default=False, db_default=False)` |
| everything else | unchanged | `module` FK, `slug`, `title`, `sort_order`, `video_url`, `body(_html)`, `homework(_html)`, `timestamps`, `is_preview`, `required_level`, `available_after_days`, `content_hash` |

`cb_unit_module_slug_unique` unchanged in shape (`module`, `slug`) — a unit's module is already
the correct uniqueness scope whether that module is top-level or a submodule.

### `CohortModule` (new)

```python
class CohortModule(models.Model):
    cohort = models.ForeignKey(Cohort, on_delete=models.CASCADE, related_name="module_placements")
    module = models.ForeignKey(Module, on_delete=models.CASCADE, related_name="placements")
    sort_order = models.IntegerField(default=0)

    class Meta:
        constraints = [
            UniqueConstraint(fields=("cohort", "module"), name="cb_cohort_module_pair_unique"),
            UniqueConstraint(fields=("cohort", "sort_order"), name="cb_cohort_module_sort_unique"),
        ]
```

`clean()` rejects a placement whose `module.course_id != cohort.course_id` and whose
`module.parent_id is not None` (only top-level modules are placed; a submodule is reached through
its parent, exactly like reading order already assumes in #252).

Default behaviour, no rows required: `Course.get_syllabus()` / a cohort's module list falls back
to `course.modules.filter(parent=None).order_by("sort_order", "pk")` when the cohort has no
`CohortModule` rows. This is AI Shipping Labs' entire case — one evergreen tree, one or two
cohorts, zero placement rows, zero extra Studio screens to fill in. A course only needs
`CohortModule` rows when a cohort must show a curated subset or a cohort-specific order, which is
DataTalks.Club's case (many dated cohorts per course family, each potentially different from the
current one). No terminal-homework binding lives here — that is `cb_coursework`'s concern, tied
to `Cohort` and `Course` directly today (`Homework.objects.filter(course__course=course,
slug=...)` is DataTalks.Club's existing pattern), and coursework does not import `Module` or
`Unit` at all today (verified: `grep -rn "from community_base.curriculum.models import"
community_base/coursework/*.py` only ever imports `Cohort`, `Course`, `Enrollment`,
`Certificate`). Module/Unit restructuring has zero blast radius into coursework.

### `Cohort`

Delete `curriculum_format` (`legacy`/`modules`) — there is one shape now; the field has nothing
left to discriminate. Everything else (`mode`, `start_date`/`end_date`, `registration_url`,
`hashtag`, `finished`, `visible`, `max_participants`, provenance) is unchanged; `mode` already
matches AISL's `#1674` field-for-field (confirmed by the AISL divergence comment on `#252`).

### Models deliberately not lifted from DataTalks.Club

- No `SharedCurriculum` wrapper row. DataTalks.Club needed it because their `Course`/`Cohort`
  split has migration history the package does not carry; `Module.course` alone gives the same
  "one tree per course" query surface (`Module.objects.filter(course=x, parent=None)`) with one
  fewer table.
- No `Shared*` naming anywhere. The package's model is simply `Module`/`Unit` — there is no
  competing legacy shape inside the package to disambiguate from, so the prefix would only be
  scar tissue from DataTalks.Club's own migration.
- No `CurriculumRouteAlias`. That is DataTalks.Club's own URL/SEO compatibility table for its own
  route history; it has no meaning to a package with no prior public route contract.
- No `CurriculumFlowItem`. It exists in DataTalks.Club only to interleave legacy per-cohort
  `Module` rows with `Project` rows in one ordered list. Once curriculum is course-owned,
  top-level `Module.sort_order` already is that order; interleaving projects into it (if ever
  needed) is `cb_coursework`'s ordering problem to solve against `CohortModule`, not curriculum's.
- No `SharedLessonReadState`. It is a passive "viewed" marker, a different concept from the
  package's existing `UnitProgress.completed_at` (an explicit completion toggle, which both sites
  already use this way). Keep `UnitProgress` unchanged; do not add a second, weaker tracking
  concept.
- No `SharedCurriculumAsset` (managed image/code-file storage for lesson content). Real capability
  gap, but orthogonal to the ownership question — the two curriculum parsers have never modelled
  assets, and `content_sync` already has an S3 media backend general-purpose enough to reuse
  later. Flagged as a follow-up issue, not solved here.
- No `CohortBuildItem`. Marketing display content, unrelated to curriculum structure.

## 3. Migration path

`community_base.curriculum` has never been tagged: `git tag --list` tops out at `v0.3.9`; `C5.3`
("Release 0.6.0") is `todo` in `docs/plan/STATUS.md`; both sites are pinned below it
(`AI-Shipping-Labs/website` at `v0.3.9`, `DataTalksClub/website` at `v0.3.0`, neither of which
carries curriculum at all — `pyproject.toml` in both repos, checked directly). `A5.1`/`D5.1`
(site adoption) are both still `todo`. There is no tagged contract to break and no live consumer
to migrate.

Per `docs/02-architecture.md` rule 5 ("append-only after a tag"), the existing
`community_base/curriculum/migrations/0001_initial.py` may be edited in place rather than
appended to, since it has never shipped in a tag. Recommendation: regenerate it after the model
changes (`makemigrations cb_curriculum`) rather than layering an `0002` alter on top of a
migration nobody has run outside this repository's own CI and `testproject`. `cb_coursework`'s
`0001_initial.py` needs no change (confirmed above: no FK to `Module`/`Unit`).

This is a breaking change to merged-but-unreleased code, managed as follows, stated plainly per
the owner's instruction rather than engineered around:

- Every existing test in `tests/curriculum/` (1,797 lines across `test_models.py` (20),
  `test_import.py` (10), `test_services.py` (23), `test_views.py` (22), `test_studio.py` (10),
  `test_staff_api.py` (10), `test_sync.py` (7), `test_access.py` (11) — 113 tests total) that
  constructs a `Module(cohort=...)` breaks and needs a mechanical update to `Module(course=...)`.
  The fixtures in `tests/curriculum/fixtures/` and the factory helpers need the same update.
- `parsers_aisl.py`, `parsers_dtc.py`, `source.py`, `importing.py`: real rewrite, not mechanical.
  `CohortGraph.modules` (owned subtree) becomes `CourseGraph.modules` (owned tree, recursive via
  `children`) plus an optional `CohortGraph.module_refs` (ordered top-level module identifiers a
  cohort places; `None` means "the full course tree, in module order" — AI Shipping Labs' parser
  always emits `None`). Nested module directories parse recursively in both parsers per `#252`'s
  numeric-prefix convention.
- `views.py`, `services.py`, `api_views.py`, `studio_views.py`: every `cohort.modules.all()` /
  `Module.objects.filter(cohort=...)` becomes `course.modules.filter(parent=None)` (default path)
  or a `CohortModule`-driven query (curated path). `get_all_units_ordered`, `get_next_unit`,
  `get_prev_unit`, `decide_unit_drip` are rewritten to the depth-first order and the
  module-then-parent-module `available_after_days` cascade specified in `#252`/`#1674`.
- Public URLs drop the cohort segment for module/unit pages: `/courses/<slug>/<module_slug>` and
  `/courses/<slug>/<module_slug>/<unit_slug>`, no cohort segment — which is not a new departure,
  it is what AI Shipping Labs' real site already serves today (confirmed in `#1674`'s backward-
  compatibility section, same paths named). The package's current cohort-scoped path
  (`/courses/<slug>/<cohort_slug>/<module_slug>/<unit_slug>`) is the thing that never matched
  either site; dropping it is a correction, not a regression.
- Studio: module/unit screens move from "pick a cohort, then a module" to "pick a course, then a
  module tree"; cohort screens gain an optional module-placement editor for the curated case.

None of this touches `Enrollment`, `UnitProgress`, `Certificate`, `CurriculumImportRun`, or
anything in `cb_coursework` (verified no cross-import above).

## 4. How #252's fields land (summary; full field tables in section 2)

`Module.parent`, `Module.is_bonus`, `Module.available_after_days`; `Unit.kind`,
`Unit.session_position`, `Unit.is_bonus` — all land on the course-owned `Module`/`Unit` directly,
not on a `Shared*`-prefixed pair and not on the current cohort-owned `Module`. Depth-first reading
order (module in `sort_order`, then its own units if it has no children, else each child's units
in order) is implemented once in `services.get_all_units_ordered`, reused by `get_next_unit`,
`get_prev_unit` and the progress percentage. Progress denominator excludes `is_bonus`
(module or unit) and includes `kind="event"` — both owner decisions on `#252`, unchanged by this
document. No `Unit.event` FK, per the divergence already recorded on `#252`.

## 5. AI Shipping Labs' A5.1 mapping, revised

The original `phase-5.md` C5.1a table assumed cohort-owned `Module`. With this design, A5.1
becomes a closer field-for-field mapping than originally planned, because AI Shipping Labs' real
model was already course-owned and `#1674` already anticipated every nested field:

| AISL `content` field | Package `cb_curriculum` field | Change from original A5.1 plan |
|---|---|---|
| `Course.*` | `Course.*` | unchanged |
| `Module.course` | `Module.course` | was `Module.cohort` in the original plan; now a direct match, not a synthesis through an invented self-paced cohort |
| `Module.parent`, `.is_bonus`, `.available_after_days` | same names | new in both; direct match, no mapping needed |
| `Unit.module`, `.kind`, `.session_position`, `.is_bonus` | same names | new in both; direct match |
| `Cohort.mode`, `.start_date`, `.end_date` | same names | already matched before this document (`#1674`'s divergence comment) |
| `Enrollment`, `UserCourseProgress`, `CourseCertificate` | `Enrollment`, `UnitProgress`, `Certificate` | unchanged |
| (none — AISL has no per-cohort module subsetting) | `CohortModule` | AISL populates zero rows; every cohort shows the full course tree by construction |

A5.1 no longer needs to synthesize a `self_paced` cohort to hold modules that logically belong to
the course — the package now agrees with AISL that they belong to the course.

## 6. What DataTalks.Club must change to fit (not built here; their agent owns their repository)

- Map `SharedCurriculum` away entirely (its only job, holding `parser_version`/`updated_at` per
  course, can sit directly on `Course` if DataTalks.Club wants it, or be dropped — the package
  does not need the row).
- Map `SharedModule` -> `Module` (add `course` FK; DataTalks.Club's `position` becomes
  `sort_order` to match the package's and AISL's existing convention).
- Map `SharedLesson` -> `Unit` (`position` -> `sort_order`).
- Map `CohortSharedModule` -> `CohortModule`, minus `terminal_homework` (moves to their own
  coursework-equivalent linkage, same as the package's `cb_coursework` keeps it out of curriculum).
- Retire `CurriculumRouteAlias`, `CurriculumFlowItem`, legacy `Module`/`Unit`,
  `SharedLessonReadState` on their own migration timeline — package adoption does not require
  DataTalks.Club to have finished retiring them first, since D5.1/D5.2 are their own freeze-gated
  cutover issues, unaffected in sequencing by this document.
- Their per-cohort module curation (the reason `CohortSharedModule`/`CohortModule` exists at all)
  is fully expressible in the new shape; nothing about DataTalks.Club's real requirement is lost,
  only DataTalks.Club-specific naming and compatibility tooling.

## 7. What AI Shipping Labs should build locally right now — read this before continuing #1674

No field name or shape in `#1674` needs to change because of this document. `Module.parent`,
`Module.is_bonus`, `Module.available_after_days`, `Unit.kind`, `Unit.session_position`,
`Unit.is_bonus`, `Cohort.mode` are exactly what the package will use too, because `#1674`'s design
was read directly off AI Shipping Labs' own already-course-owned model and this document targets
that same model. The one thing that does NOT carry over to the future package migration
mechanically: `#1674` still expresses `Module.available_after_days`/drip and read order as
site-local service functions (`content/services/course_units.py`); when `A5.1` eventually runs,
those functions are deleted in favour of `community_base.curriculum.services`, not mapped
field-by-field, because they become the same functions, not site-specific ones. That was already
true before this document and remains true after it. Continue `#1674` as scoped.

## 8. Open follow-ups this document intentionally does not resolve

- `SharedCurriculumAsset`-equivalent (managed lesson images/code files) — real gap, own issue.
- Whether `CohortModule.sort_order` needs a `db_default` — it does not (it has a Python
  `default=0`, and the column is not nullable but every existing row at migration time is a fresh
  table, so this is new-model, not new-column-on-existing-table; the "every new column needs a
  database-level default" quality bar applies to columns added to a table with existing rows
  during a rolling deploy, which does not apply to a brand-new, never-released table). Flagged
  explicitly so the implementer does not skip it by oversight rather than by this reasoning.
